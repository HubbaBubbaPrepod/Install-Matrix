# Architecture

> [Русская версия](ARCHITECTURE.ru.md)

Install-Matrix targets one dedicated Ubuntu/Debian VPS. Nginx is the only public HTTP entry point; application ports bind to loopback or an isolated Compose network.

```text
Clients / federation
         │ HTTPS :443
         ▼
       Nginx ─────────────── .well-known on server_name
         │
         ├── Synapse :8008 ─── PostgreSQL
         ├── MAS :8080 ─────── MAS PostgreSQL
         ├── lk-jwt :8082 ──── LiveKit (host network)
         ├── admin UIs
         └── ntfy :8090

Calls ── TURN/TLS ── Coturn (host network)
Calls ── MatrixRTC ─ LiveKit (host network)
```

## Trust boundaries

- Internet → Nginx/Coturn/LiveKit: untrusted public traffic.
- Nginx → loopback services: reverse-proxy boundary.
- Compose `matrix` network: application/database traffic.
- `/root/matrix-server`: root-owned secrets, configuration and persistent state.
- offsite backup storage: encrypted recovery boundary.

## Generated files

```text
/root/matrix-server/
├── .env
├── docker-compose.yml
├── credentials.txt
├── federation-domains.txt
└── data/
    ├── postgres/
    ├── synapse/
    ├── coturn/
    ├── mas/
    ├── mas-db/
    ├── livekit/
    ├── ketesa/
    ├── element-admin/
    ├── ntfy/
    └── backups/
```

The generated Compose file is intentionally treated as output. Persistent configuration belongs in `.env` and is regenerated by the installer.

## Installer layout

`install-matrix.sh` deliberately remains a standalone release artifact: an operator can download, inspect and verify one file before running it. Functions are grouped by lifecycle boundary (rendering, components, backup/restore, update/rollback, diagnostics and CLI), while `tests/` exercises those boundaries independently. `scripts/build-release.sh` creates the immutable distributable and checksum manifest; generated runtime files are not maintained as a second source tree.
